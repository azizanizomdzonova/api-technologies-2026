## 2. Границы REST API
* **Внешние потребители:**
  1. **Автоматизированная банковская система (АБС)** — главный потребитель. Передает события транзакций и получает вердикт.
  2. **Команда аналитиков** — передает новые версии ML-моделей в систему.
  3. **Внешние источники данных** — предоставляют дополнительную информацию о клиенте (возраст, геолокация).
  4. **Клиент банка** — косвенный потребитель, инициирует транзакции через приложение банка.

* **Внешние системы:** 
  * АБС (Автоматизированная банковская система) — источник транзакций.
  * Внешние источники данных — поставщики данных о клиенте.

* **Проектируемые сервисы (из контейнерной диаграммы):**
  * Точка входа (Gateway) — прием событий.
  * Дополнение данных (Enrichment) — обогащение данных о клиенте.
  * Статистика клиента (Features) — агрегация данных.
  * ML-сервис — инференс модели.
  * Решение (Rules) — вынесение вердикта 1/0.

## 3. Взаимодействие сервисов
* **Внутренние взаимодействия (REST):**
  * **АБС -> Точка входа (Gateway):** Отправляет событие транзакции (JSON), получает вердикт (1/0).
  * **Точка входа -> Дополнение данных (Enrichment):** Передает данные для обогащения.
  * **Дополнение данных -> Статистика клиента (Features):** Запрашивает агрегированные данные по клиенту.
  * **Статистика клиента -> ML-сервис:** Передает признаки для инференса модели.
  * **ML-сервис -> Решение (Rules):** Передает результат предсказания для финального вердикта.
  * **Решение -> АБС:** Возвращает итоговый вердикт (1 — подтверждено, 0 — отклонено).

* **Внешние взаимодействия:**
  * Система обращается ко **Внешним источникам данных** (для получения сведений о клиенте).
  * Система получает **новые версии ML-моделей** от команды аналитиков.

## 4. Обоснование методов и путей
* **Используется GET** для чтения данных (получение статуса, истории, статистики клиента), потому что это идемпотентные операции, которые не меняют состояние системы.
* **Используется POST** для операций, требующих сложной обработки входящих данных или создания новых ресурсов. В случае с проверкой транзакций (`/v1/transactions/evaluate`) метод POST позволяет безопасно и структурированно передавать объемные JSON-данные в теле запроса (Request Body), избегая ограничений и рисков передачи информации через URL-параметры. Также данный метод применяется для загрузки новых сущностей в систему (например, новых версий ML-моделей через `/v1/models`).
* Пути (paths) строятся по принципу `/ресурс/идентификатор` или `/ресурс/действие`, например `/v1/transactions/evaluate` или `/v1/clients/{client_id}`.

## 5. Обработка ошибок
* Единый формат ошибки: `{ "code": "STRING", "message": "Описание ошибки" }`
* **400 Bad Request:** Неверный формат входных данных (некорректный JSON, отсутствуют обязательные поля).
* **404 Not Found:** Запрашиваемый объект (транзакция, клиент, эндпоинт) не найден.
* **422 Unprocessable Entity:** Ошибка валидации данных (например, отрицательная сумма транзакции).
* **500 Internal Server Error:** Ошибка на стороне сервиса (например, падение ML-модели).
* **503 Service Unavailable:** Внешний сервис (например, источники данных) недоступен.

## 6. Особенности кейса (Ограничения)

* **Требования к Latency (Время ответа):** Взаимодействие с АБС при проверке транзакции (`POST /v1/transactions/evaluate`) является синхронным на уровне REST API. АБС удерживает соединение и ожидает вердикта. Жесткий SLA по времени ответа составляет не более **100 мс**.
* **Особенности данных (Кэширование):** Для удержания SLA в 100 мс система не делает «тяжелых» запросов в базы данных во время проверки. Необходимая статистика по клиентам заранее агрегируется и загружается в кэш (Redis) для мгновенного доступа (1-3 мс).
* **Требования к Throughput (Пропускная способность):** Синхронный характер API-контракта не является узким местом при высоких нагрузках. Для обработки потока в десятки тысяч транзакций в секунду (RPS) система опирается на горизонтальное масштабирование внутренних сервисов. Все вторичные процессы, не влияющие на сиюминутный вердикт (сохранение истории транзакций, обновление витрин, логирование), выполняются строго асинхронно через брокер сообщений, не блокируя HTTP-ответ для АБС.

## Описание REST-операций 

### 1. Back API: Точка входа (Gateway) - Проверка транзакции
* **Назначение:** Оценка банковской транзакции на мошенничество.
* **Потребитель:** Автоматизированная банковская система (АБС).
* **Метод и путь:** `POST /v1/transactions/evaluate`
* **Параметры пути и запроса:** Отсутствуют.
* **Необходимые заголовки:**
  * `Content-Type: application/json` — указывает, что данные передаются в формате JSON.
  * `X-Request-ID` — уникальный номер запроса (нужен для сквозного поиска логов при ошибках).
* **Тело запроса (Request Body):** Обязательное, передается в формате JSON. Содержит поля:
  * `transaction_id` (string) — уникальный ID транзакции из АБС.
  * `account_id` (string) — идентификатор счета клиента.
  * `amount` (number) — сумма транзакции (строго больше 0).
  * `timestamp` (string) — время отправки транзакции.
  * `currency` (string, по умолчанию `RUB`) — валюта операции.
* **Успешный статус и схема ответа:**
  * `200 OK` — Вердикт готов. Возвращает JSON с полями `transaction_id`, `verdict` (где 0 - Одобрено, 1 - Фрод) и `evaluated_at`.
* **Применимые ошибки:** 
  * `400 Bad Request` — АБС прислала нечитаемые/битые данные.
  * `404 Not Found` — Эндпоинт не найден.
  * `422 Unprocessable Entity` — Ошибка валидации (например, отрицательная сумма транзакции).
  * `500 Internal Server Error` — Ошибка на стороне бэкенда системы.

### 2. Front API: Внешнее API антифрод-системы

**А. Получение данных клиента из внешних источников**
* **Назначение:** Обогащение данных (Enrichment) при проверке транзакции.
* **Метод и путь:** `GET /v1/clients/{client_id}`
* **Параметры пути (path):**
  * `client_id` (string, обязательный) — уникальный ID клиента.
* **Тело запроса:** Отсутствует.
* **Успешный статус и схема ответа:**
  * `200 OK` — Данные клиента найдены (возвращает объект с полями `client_id`, `age`, `geo`).
* **Применимые ошибки:** 
  * `400 Bad Request` — Неправильный формат ID клиента.
  * `404 Not Found` — Клиент не найден во внешнем источнике. 
  * `500 Internal Server Error` — Внешний источник недоступен.

**Б. Загрузка новой ML-модели от аналитиков**
* **Назначение:** Передача аналитиками новой версии модели машинного обучения для сохранения в хранилище.
* **Метод и путь:** `POST /v1/models`
* **Параметры:** Отсутствуют.
* **Тело запроса (Request Body):** Обязательное, формат JSON. Содержит:
  * `name` (string) — название ML-модели.
  * `version` (string) — версия загружаемой модели.
* **Успешный статус и схема ответа:**
  * `201 Created` — Модель успешно загружена (возвращает объект со статусом: `{ "status": "Model uploaded successfully" }`).
* **Применимые ошибки:** 
  * `400 Bad Request` — Не хватает `name` или `version`.
  * `409 Conflict` — Модель с такой версией уже существует
  * `500 Internal Server Error` — Не удалось сохранить модель.

**В. Получение списка ML-моделей**
* **Назначение:** Запрос списка всех доступных версий моделей в системе.
* **Метод и путь:** `GET /v1/models`
* **Тело запроса:** Отсутствует.
* **Успешный статус и схема ответа:**
  * `200 OK` — Список моделей успешно получен (возвращает массив объектов с полями `name`, `version`, `status`).
* **Применимые ошибки:** 
  * `500 Internal Server Error` — Не удалось получить список моделей.
